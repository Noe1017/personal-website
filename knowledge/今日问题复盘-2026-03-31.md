## 2. Spark OOM 与数据倾斜

### 2.1 Spark OOM 先分两类
- `Driver OOM`
- `Executor OOM`

### 2.2 Driver OOM 常见原因
- `collect()` / `toPandas()` 拉太多数据到 Driver
- 广播变量过大
- 小文件 / 分区 / task 过多，Driver 维护的元数据过大
- SQL / DAG 太复杂，执行计划太大

### 2.3 Executor OOM 常见原因
- 数据倾斜导致少数 task 吃到超大 partition
- shuffle / join / 聚合内存压力过大
- cache 过多
- 单分区太大
- 广播表过大

### 2.4 数据倾斜和 OOM 的关系
- 数据倾斜不一定导致 OOM。
- 它的本质是：
  - `负载不均衡`
- 常见结果：
  - 长尾 task
  - 吞吐下降
  - 资源利用不均
  - Flink 场景下反压、checkpoint 变慢
- 严重时才会演化成 OOM。

## 3. Spark Shuffle / AQE / Join

### 3.1 reduceByKey 和 groupByKey 的区别
- 共同点：
  - 都按 key 分组
- `reduceByKey`
  - 可以在 map 端先局部聚合
  - shuffle 数据量更小
  - 性能通常更好
- `groupByKey`
  - 只是把同 key 的所有 value 聚到一起
  - 不做 map-side combine
  - 更容易引发大 shuffle、倾斜和 OOM

### 3.2 AQE 是什么
- `AQE = Adaptive Query Execution`
- 核心：
  - 先按初始计划跑
  - 等 shuffle 后拿到真实统计信息
  - 再动态调整后续物理计划

### 3.3 AQE 常见能力
- 合并过小 partition
- 识别并拆分倾斜 partition
- 动态调整 join 策略
  - 比如 `SortMergeJoin -> BroadcastHashJoin`

### 3.4 AQE + skew join 的本质
- 根据 shuffle 后各 partition 的真实大小识别热点分区
- 把大 partition 拆成多个更小任务
- 在 join 场景下可把另一侧对应小分区复制给多个拆分任务
- 目标：
  - 缓解长尾 task
  - 降低倾斜导致的慢和 OOM 风险

### 3.5 Sort Merge Join 改成 Broadcast Join
- 原始计划：
  - 双边 shuffle + 排序后再 join
- AQE 运行时发现其中一边实际很小
- 动态改成：
  - 小表广播到各 Executor
  - 本地做 hash join
- 好处：
  - 减少 shuffle
  - 减少排序开销

### 3.6 Shuffle 的本质
- 本质不是“map 和 reduce”本身，而是：
  - `按新的 key 重新分区和重分布数据`
- `map side` 和 `reduce side` 是 shuffle 两侧的职责分工。

### 3.7 Shuffle 中 map / reduce 具体做什么
- `map side`
  - 读取本 partition 数据
  - 根据 key 计算目标 partition
  - 按 partition 切分数据
  - 可能本地排序 / combine
  - 写出 shuffle 中间结果
- `reduce side`
  - 按自己的 partition id
  - 从所有上游 map task 拉取属于自己的那部分数据
  - 本地 merge
  - 做聚合、join、排序等后续计算

### 3.8 count(distinct) 在哪侧完成
- 最终全局 distinct 结果通常在 `reduce side` 完成。
- map 侧最多做局部预聚合 / 局部去重，减少 shuffle 数据量。

## 4. Flink 资源、反压与积压

### 4.1 TaskManager 和 slot 的关系
- `TaskManager`
  - Flink 真正执行任务的 worker 进程
- `slot`
  - TaskManager 内部的资源配额单位
- 关系：
  - Flink 把 subtask 调度到某个 TaskManager 的某个 slot 上运行
- 注意：
  - slot 不是线程
  - 也不一定一对一对应一个 task

### 4.2 Kafka 分区数、Flink 并行度、slot 数关系
- Kafka partition 数：
  - 决定 source 最多能并行消费多少份数据
- Flink 并行度：
  - 决定算子拆成多少个 subtask
- slot 数：
  - 决定集群能同时承载多少个 subtask
- 一句话：
  - `partition 约束读，parallelism 约束算，slot 约束装载能力`

### 4.3 什么是算子反压
- 本质：
  - 下游处理不过来
  - 上游数据发不出去
  - 压力沿链路向上游传导
- 常见结果：
  - 吞吐下降
  - 延迟升高
  - source 消费变慢
  - 严重时可能带来 checkpoint 变慢和 OOM

### 4.4 什么是消费积压
- 本质：
  - 生产速度 > 消费速度
- 常见表现：
  - Kafka lag 持续增长
- 常见关系：
  - 作业内反压向上传导到 source，最终形成积压

### 4.5 反压与积压的关系
- 常见情况：
  - `反压是内因，积压是外在表现之一`
- 但也不是绝对：
  - 上游流量突增、partition 不够、source 并行度不足时，也可能先出现积压

### 4.6 busy / idle / backPressured time
- `busy time`
  - 算子真正忙着处理数据的时间占比
- `idle time`
  - 算子没数据可处理的时间占比
- `backPressured time`
  - 因为下游堵塞，数据发不出去而被阻塞的时间占比

### 4.7 这三个指标怎么判断问题
- `busy high`
  - 当前算子自己计算重
- `idle high`
  - 当前算子不是瓶颈，可能上游没喂饱
- `backPressured high`
  - 当前算子更像被下游卡住

### 4.8 算子反压常见处理手段
- 提高并行度、扩容资源
- 优化重逻辑 UDF、解析、序列化
- 热 key 打散、两阶段聚合
- 状态瘦身、TTL、缩小窗口
- 优化 RocksDB / checkpoint
- 提高 sink 并行度，改异步 / 批量写

### 4.9 消费积压常见处理手段
- 提高 source 并行度
- 增加 Kafka partition
- 解决作业内反压链路
- 优化 sink 吞吐
- 必要时扩资源、限流、削峰

## 5. ClickHouse 和 Doris

### 5.1 两者共同点
- 都是列式 OLAP 数据库
- 都依赖：
  - 列式存储
  - 向量化执行
  - MPP 并行
  - 高压缩
  - 分区裁剪 / 预聚合

### 5.2 区别
- `ClickHouse`
  - 更偏极致查询性能
  - 更强调围绕查询性能做表设计
- `Doris`
  - 更偏实时数仓和 BI 场景
  - 表模型、导入体系、产品化能力更完整

### 5.3 关于 BI 和表模型的更严谨说法
- 不能说 ClickHouse 没有 BI 场景，也不能说它没有表模型。
- 更准确是：
  - ClickHouse 也能支撑 BI，也有自己的建模方式
  - 只是 Doris 在实时数仓和企业 BI 友好性上通常更强、更直接

## 6. SQL 笔试题

### 6.1 商品维表增量更新
- 场景：
  - `dim_item` 为前一天全量维表
  - `item_update_log` 为当天变更日志
- 核心思路：
  - 先按 `item_id` 取当天最后一条变更
  - 前一天全量减去这些发生最终变更的旧记录
  - 再把当天最终 `insert/update` 的记录补进去
  - 最终 `delete` 的商品不再保留

### 6.2 给维表分配连续编号
- 如果要求：
  - 从 1 开始
  - 连续
  - 不重复
- 本质就是：
  - 全局编号
- 标准做法：
  - `row_number() over(order by item_id)`
- 注意：
  - 如果要求严格连续，基本绕不开全局排序 / 全局编号

### 6.3 分钟级趋势图：累计 PV / UV
- 分钟级 `PV`
  - 先截到分钟，再按分钟统计，最后做累计和
- 累计 `UV`
  - 不能直接对每分钟 UV 求和
  - 正确做法：
    - 先找每个用户首次访问分钟
    - 按分钟统计新增 UV
    - 再对新增 UV 做累计

### 6.4 大表 join 大表防倾斜
- 场景：
  - A 表 `50TB`
  - B 表 `10TB`
  - 按 `item_id` join
- 不适合直接 broadcast
- 常见解法：
  - 热点 key 单独处理
  - 非热点正常 join
  - 热点部分采用：
    - A 侧随机加盐
    - B 侧按盐值扩容复制
    - 带盐 key join
