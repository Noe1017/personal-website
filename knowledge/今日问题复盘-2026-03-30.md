# 今日问题复盘 - 2026-03-30

## 1. MetaSentry AI

### 1.1 项目定位
- `MetaSentry AI` 不是泛化的风控平台，而是 `指标资产智能审核系统`。
- 当前更准确的表述是：
  - 总体目标：面向 `指标 / 维度 / 模型` 的标准化资产审核。
  - 当前落地：先聚焦 `新建指标` 场景，支持 `字段级实时校验 + 完整资产审核`。
- 核心价值：
  - 把原来依赖人工审核的规范校验前置到资产创建环节。
  - 降低人工审核成本，提升标准执行一致性。

### 1.2 为什么要做
- 团队在新建指标资产时，容易出现：
  - 命名不统一
  - 定义不清
  - 重复建设
  - 依赖关系不合理
- 原来主要依赖人工审核：
  - 效率低
  - 标准执行不稳定
  - 新人上手成本高

### 1.3 为什么不是纯规则，而是规则 + LLM
- 纯规则适合确定性问题：
  - 必填
  - 枚举
  - 格式
  - 特殊字符
  - 禁止词
  - 单位 / 精度 / 数据类型硬约束
- LLM 更适合语义问题：
  - 定义是否完整
  - 名称和定义是否一致
  - 业务过程和量化对象是否匹配
  - 是否存在语义冲突或重复建设风险
- 一句话：
  - `规则负责确定性，LLM 负责语义理解`

### 1.4 规则类任务有哪些
- 必填校验
- 枚举值校验
- 英文名格式校验
- 特殊字符校验
- 版本词根 / 数字后缀 / 禁止词检查
- 单位、精度、数据类型规范
- 依赖关系里的硬约束
- 精确重名、全局唯一性校验

### 1.5 语义类任务有哪些
- 指标定义是否完整、是否可复现
- 名称和定义是否一致
- 业务过程、量化对象、量化方式是否匹配
- 中文名和英文名是否语义一致
- 是否与已有指标语义冲突
- 修改建议生成

### 1.6 真正难的点
- 难点 1：审核标准并没有想象中那么客观
  - 很多边界 case 不同审核人判断并不一致。
  - 真正难的是先把专家口径收敛出来，而不是直接调模型。
- 难点 2：LLM 结论波动会直接伤害可信度
  - 同一个指标稍微改几个字，如果结论来回变，业务不会信。
  - 处理方式：
    - 尽量把问题拆到字段级
    - 规则先兜底
    - 模型输出结构化结果和置信度
    - 引入 `PASS / CONDITIONAL / REJECT`
- 难点 3：业务不敢直接放权给 AI
  - 如果一上来做自动门禁，误判成本高，业务会抵触。
  - 更合理的落地方式是：
    - 先做预审和辅助决策
    - 高确定性问题直接提示修改
    - 复杂 case 保留人工兜底

### 1.7 名称审核看什么
- 规则层：
  - 是否为空、是否过长
  - 是否有非法字符
  - 是否有禁止词、版本词根、数字后缀
  - 命名结构是否符合规范
  - 修饰词顺序是否合理
- 语义层：
  - 业务过程是否明确
  - 统计对象是否明确
  - 量化词是否明确
  - 修饰词是否准确
  - 是否容易和已有指标混淆
  - 是否和定义一致

### 1.8 定义审核看什么
- 统计对象是否明确
- 业务过程是否明确
- 量化方式是否明确
- 时间范围是否明确
- 过滤条件是否明确
- 去重口径是否明确
- 依赖口径 / 数据来源是否清楚
- 是否完整、可复现
- 是否和名称一致
- 是否存在歧义或空话

### 1.9 如何判断名称和定义是否一致
- 不靠感觉，靠语义槽位比对。
- 重点比对：
  - 业务过程
  - 统计对象
  - 量化方式
  - 时间口径
  - 限定条件
- 方法：
  - 先把名称拆成 `业务过程 + 量化对象 + 量化词 + 修饰词`
  - 再从定义里抽 `对象 / 行为 / 时间 / 条件 / 去重方式`
  - 最后做对齐判断

### 1.10 如何判断口径描述是否清晰
- 核心标准不是“文字是否通顺”，而是：
  - `别人能不能不问作者，就稳定写出同一套 SQL 或计算逻辑`
- 重点看：
  - 统计对象
  - 统计行为
  - 时间范围
  - 过滤条件
  - 去重方式
  - 度量方式
  - 数据来源 / 依赖关系

### 1.11 如何判断语义冲突
- 不直接全库逐条比，而是：
  - `先召回，再精判`
- 召回阶段：
  - 名称关键词重合
  - 业务过程相同
  - 量化对象相同
  - 名称 / 定义向量相似
- 精判阶段：
  - 比较名称、定义、业务过程、量化对象、量化方式、时间范围、过滤条件
  - 再让 LLM 区分：
    - 同义不同名
    - 同名不同义
    - 高度重叠
    - 名称相似但不冲突

## 2. Flink 一致性与乱序处理

### 2.1 Flink 如何保证端到端一致性
- 核心公式：
  - `checkpoint + source 位点快照 + sink 提交语义 -> 端到端一致性`
- Flink 内部一致性：
  - operator state 做一致性快照
  - source offset 一起记录
- 真正端到端 `exactly-once` 还要求：
  - source 可回溯
  - sink 支持事务或幂等写入

### 2.2 Barrier 是什么
- `barrier` 是 checkpoint 的边界标记。
- 作用：
  - 把“checkpoint 之前的数据”和“checkpoint 之后的数据”切开。
- 它由 source 注入，和业务数据一起向下游传播。

### 2.3 什么是“所有输入”
- 这里的“所有输入”不是所有数据，而是：
  - `某个算子的所有上游输入通道`
- 比如：
  - join 有多路输入
  - 一个下游 task 也可能同时接收多个上游并行实例的数据 channel

### 2.4 Barrier Alignment 是什么
- 如果多输入算子里，某一路先收到 barrier，不能立刻做快照。
- 因为其他输入通道上，checkpoint 之前的数据可能还没处理完。
- `barrier alignment` 的做法是：
  - 先阻塞已经到 barrier 的输入通道
  - 继续处理未到 barrier 的通道
  - 等所有通道都收到同一个 barrier 后
  - 再统一 snapshot
- 本质：
  - `把多路输入对齐到同一个 checkpoint 边界`

### 2.5 Flink 如何处理乱序
- 核心靠三件事：
  - `event time`
  - `watermark`
  - `allowed lateness / side output`
- 不是按数据到达机器的时间算，而是按事件发生时间算。
- `watermark` 表示：
  - `系统当前认为某个时间点之前的数据基本已经到齐了`

### 2.6 Allowed Lateness 是什么
- 窗口第一次触发后，再额外保留一段时间。
- 这段时间内到达的迟到数据，仍然可以进入原窗口并修正结果。
- 可以理解成：
  - `窗口补账期`

### 2.7 Side Output 是什么
- 如果数据比 `allowed lateness` 还晚，就不再进入主窗口。
- 这时把数据打到旁路输出流里，做后续补偿、落库或离线修正。
- 一句话：
  - `allowed lateness` 还能补原窗口
  - `side output` 是把极端迟到数据分流出来

### 2.8 实时 5 分钟滚动窗口去重统计怎么做
- 场景：
  - 每 5 分钟滚动窗口统计：
    - 去重订单数
    - 去重活跃用户数
  - 最多允许 1 分钟乱序
- 优先选 `Flink`：
  - 原生事件时间模型更适合乱序处理
  - 状态管理和低延迟能力更强
- 精确方案：
  - `event time + watermark`
  - 对 `order_id` / `user_id` 分别做 stateful dedup
  - 下游再做窗口聚合
- 状态控制：
  - 按 key 分散状态
  - RocksDB state backend
  - TTL = 窗口长度 + 最大迟到时间
- 如果业务允许误差：
  - 可用 `HyperLogLog / APPROX_COUNT_DISTINCT`
  - 以内存换精度

### 2.9 这类题的 Flink SQL 写法
- 典型方案：
  - 源表定义 `WATERMARK FOR event_time AS event_time - INTERVAL '1' MINUTE`
  - 用 `HOP` 窗口：
    - 步长 `1 minute`
    - 窗口 `5 minute`
  - 聚合：
    - `COUNT(DISTINCT order_id)`
    - `COUNT(DISTINCT user_id)`

## 3. 高频笔试 / 面试题速记

### 3.1 连续 3 天订单金额 > 100 的用户
- 典型 SQL 思路：
  - 先过滤 `order_amt > 100`
  - 对每个用户按日期排序做 `row_number`
  - 用 `dt - rn` 分组识别连续区间
  - `having count(*) >= 3`

### 3.2 数独校验
- 思路：
  - 分别检查 9 行、9 列、9 个 `3x3` 宫
  - 每次用 `set` 判重
- 时间复杂度：
  - `O(81)`

### 3.3 RF、GBDT、XGBoost 区别
- RF：
  - `bagging`
  - 多棵树独立训练
  - 核心是降方差
- GBDT：
  - `boosting`
  - 串行拟合残差 / 负梯度
  - 核心是降偏差
- XGBoost：
  - GBDT 的增强版
  - 二阶优化、正则化、剪枝、缺失值处理、工程优化更强

### 3.4 单树、RF、GBDT 的偏差方差
- 单棵深树：
  - 低偏差、高方差
- RF：
  - 方差显著下降
  - 偏差略升或接近单树
- GBDT：
  - 更擅长降偏差
  - 方差风险通常高于 RF
- 选型启示：
  - 偏差高，优先 Boosting
  - 方差高、过拟合重，优先 RF

### 3.5 一笔走完迷宫所有格子
- 本质：
  - 网格图上的 `Hamilton Path`
- 典型解法：
  - `DFS + 回溯`
- 关键剪枝：
  - 连通性剪枝
  - 度数剪枝
  - 按后续可选邻居数排序
  - 奇偶性剪枝
