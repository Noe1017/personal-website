# 今日问题复盘 - 2026-03-18

## 1. Flink 一致性与时间语义

### 1.1 Flink 如何保证数据一致性
- 核心可以概括为：
  `checkpoint 保证状态一致性 + source offset 一致性 + sink 提交语义 -> 端到端一致性`
- Flink 会定期做 `checkpoint`。
- checkpoint 本质上是：
  - 对算子状态的一次一致性快照
  - 对 source 消费位点的一次一致性快照
- 任务失败时：
  - 状态恢复到最近成功 checkpoint
  - source 位点也回滚到对应 checkpoint
- 如果 sink 支持幂等写入或两阶段提交，就可以进一步保证结果一致性。
- 理想情况下可以做到：
  - `exactly-once`

### 1.2 Checkpoint 和 Savepoint 的区别
- `checkpoint`：
  - 系统自动触发
  - 主要用于故障恢复
  - 高频、轻量、偏运行时容错
- `savepoint`：
  - 通常人工触发
  - 主要用于升级、迁移、暂停恢复
  - 更可控、可保留、偏运维管理
- 一句话：
  - `checkpoint` 是系统自动打的恢复点
  - `savepoint` 是人工保留的状态存档点

### 1.3 Barrier 对齐机制
- `barrier` 是 Flink checkpoint 的边界标记。
- 它由 source 注入数据流，和业务数据一起向下游传播。
- 多输入算子里，不同输入流到达 barrier 的时间可能不同。
- 为了保证 checkpoint 一致性：
  - 先到 barrier 的输入会先被暂时阻塞
  - 等其他输入也到达同一个 checkpoint barrier
  - 所有输入对齐后，再对当前状态做快照
  - 然后 barrier 再继续向下游传播
- 本质：
  - `让多路输入在同一个 checkpoint 边界上对齐`
- 代价：
  - 可能带来等待、延迟和背压

### 1.4 Watermark 是什么，作用是什么
- `watermark` 可以理解成事件时间的进度线。
- 它用来告诉 Flink：
  - 某个时间点之前的数据基本已经到齐了
- 主要作用：
  - 推进事件时间
  - 触发事件时间窗口计算
  - 判断迟到数据
- 没有 watermark：
  - 系统就不知道事件时间窗口什么时候该关闭
- 一句话：
  - `watermark 是事件时间进度标记，作用是触发窗口和判断迟到数据`

## 2. Flink Join

### 2.1 Interval Join 是什么
- `interval join` 是基于时间区间的双流关联。
- 关联条件一般有两个：
  - `key` 相同
  - 事件时间差落在指定区间内
- 典型场景：
  - 订单流 join 支付流
  - 请求流 join 响应流
  - 点击流 join 曝光流
- 一句话：
  - `把两条流中 key 相同、时间差落在指定区间内的数据关联起来`

### 2.2 Left Interval Join 和 Inner Interval Join 的区别
- `inner interval join`：
  - 只输出匹配成功的数据
  - 没匹配上就不输出
- `left interval join`：
  - 保留所有左流数据
  - 如果没匹配到右流，右侧字段补 `null`
- 一句话：
  - `inner` 只保留匹配成功的记录
  - `left` 保留左侧全部记录

### 2.3 没匹配上会怎么样
- `inner join`：
  - 没匹配上，直接不输出
- `left join`：
  - 没匹配上，左侧保留
  - 右侧补 `null`

### 2.4 会不会等待匹配
- 会。
- 因为流式 join 不是一次性拿到全量数据，而是要等后续数据是否会到。
- `inner join`：
  - 如果暂时没匹配上，会先等
  - 等到时间区间结束，仍然没匹配上，就不输出
- `left join`：
  - 不能一上来就输出 `right = null`
  - 因为后面在区间内仍然可能有右流数据到来
  - 要等到 watermark 证明“后面已经不可能再匹配上”时，才能输出空值结果
- 一句话：
  - `等待的是未来是否还有匹配可能`

## 3. Spark SQL 执行与 Job 划分

### 3.1 Spark SQL 是如何划分 Job 的
- 核心原则：
  - `按 action 划 Job`
- `spark.sql(...)` 本身通常不会立刻执行。
- 真正触发执行的是：
  - `show`
  - `count`
  - `collect`
  - `write.save`
- 一次 action，通常对应一次 Job。
- 同一条 SQL，如果连续调用：
  - `df.count()`
  - `df.show()`
- 通常会形成两个 Job。

### 3.2 为什么同一条 SQL 会触发多个 Job
- 因为 SQL / DataFrame 本质上是：
  - 一个懒执行的计算计划
  - 不是已经算好的结果
- 每次 action 都是在向 Spark 发起一次新的结果请求。
- 所以：
  - `count()` 要跑一遍拿条数
  - `show()` 又要跑一遍拿展示结果
- 如果没有 cache，中间结果可能会被重复计算。

### 3.3 Job、Stage、Task 的关系
- `Job`：
  - 一次 action 触发的一次完整执行
- `Stage`：
  - Job 内按 shuffle 边界划分的阶段
- `Task`：
  - Stage 在单个 partition 上的执行单元
- 记忆方式：
  - `Action -> Job -> Stage -> Task`

### 3.4 SQL 里的哪些东西影响 Job，哪些影响 Stage
- 影响 `Job` 的核心是：
  - `action`
- 影响 `Stage` 的核心是：
  - `shuffle`
- 比如：
  - `show`、`count`、`write.save` 决定什么时候提交 Job
  - `join`、`group by`、`order by`、`distinct` 决定 Job 内如何切 Stage
- 不要把两者混起来。

### 3.5 一个 Spark SQL 可能在哪些阶段有 action
- 严格说：
  - SQL 中间的 `select`、`where`、`join`、`group by`、`order by` 都不是 action
- action 一般发生在结果阶段：
  - `df.show()`
  - `df.count()`
  - `df.collect()`
  - `df.write.save(...)`
- 更底层一点：
  - 一次 action 执行过程中，Spark 内部有时也会因为 broadcast 或子查询物化等原因额外产生 Job
- 但面试默认口径还是：
  - `用户显式写出来的 show/count/write 才是最重要的 action`

### 3.6 show、count、write 的关系
- `show`：
  - 展示部分结果
  - 是 action
- `count`：
  - 返回结果集条数
  - 是 action
- `write`：
  - `df.write` 本身更像写出入口
  - 真正触发执行的是：
    - `save`
    - `insertInto`
    - `saveAsTable`
- 它们的共同点：
  - 都会让 Spark 从懒执行进入真正执行

## 4. Spark SQL 执行计划

### 4.1 执行计划是如何生成的
- Spark SQL 生成执行计划的大致过程是：
  - `SQL -> 语法解析 -> 逻辑计划 -> Analyzer 语义解析 -> Optimizer 逻辑优化 -> 物理计划 -> action 触发执行`
- 逻辑计划回答的是：
  - `做什么`
- 物理计划回答的是：
  - `具体怎么做`
- 比如：
  - 逻辑计划只知道这里要 join
  - 物理计划才会决定是 `BroadcastHashJoin` 还是 `SortMergeJoin`

### 4.2 Optimizer 会做哪些逻辑优化
- 核心目标：
  - `不改变语义的前提下，尽量少读、少传、少算`
- 常见优化包括：
  - 谓词下推
  - 列裁剪
  - 常量折叠
  - 表达式简化
  - 子查询改写
  - 冗余算子消除
  - 为 join / 聚合做更优逻辑改写
- 一句话：
  - `先把逻辑计划改写成等价但更优的形式，再交给物理计划选择器`

## 5. MetaSentry AI

### 5.1 为什么这个项目要用 LLM，而不是纯规则
- 因为审核问题里既有确定性问题，也有语义问题。
- 适合规则的部分：
  - 必填
  - 格式
  - 枚举
  - 命名结构
- 适合 LLM 的部分：
  - 定义是否完整
  - 名称与定义是否一致
  - 业务过程和量化对象是否匹配
  - 是否和存量指标语义冲突
- 所以合理方案是：
  - `规则优先，LLM 补语义`
- 不是纯规则，也不是纯大模型。

### 5.2 项目里的 RAG 是怎么做的
- 更准确的说法是：
  - `这是面向指标审核场景的检索增强审核`
- 核心思路：
  - 先检索和当前指标最相关的规范、历史资产和上下文
  - 再把这些内容连同待审核表单一起交给 LLM
- 检索的数据源可以包括：
  - 命名规范
  - 审核标准
  - 存量指标名称和定义
  - 依赖关系和主题模型信息
- RAG 在这里的作用不是替代规则，而是：
  - 给 LLM 补上下文
  - 降低幻觉
  - 让审核结果更贴业务规范

## 6. RAG、Embedding、MCP 的关系

### 6.1 什么是 RAG
- `RAG = Retrieval-Augmented Generation`
- 中文一般叫：
  - `检索增强生成`
- 核心流程：
  - 先检索相关资料
  - 再让模型基于资料生成答案

### 6.2 大模型是如何使用 RAG 知识库的
- 大模型不是直接“自己去读知识库”。
- 更准确地说：
  - 系统先从知识库里检索相关内容
  - 再把检索结果拼进 prompt
  - 模型基于这些上下文生成答案
- 所以是：
  - `先检索，再生成`

### 6.3 Embedding 和 RAG 的关系
- `embedding`：
  - 把文本映射成向量
  - 用于语义相似度检索
- `RAG`：
  - 是一整套检索增强生成方案
- 两者关系：
  - `embedding 常常是 RAG 检索层的重要基础`
- 但 embedding 本身不等于 RAG。

### 6.4 能不能说“大模型通过 MCP 调用 embedding 以后的知识库”
- 可以表达这个意思，但不够严谨。
- 更准确的说法是：
  - `大模型通过 MCP 调用检索工具或知识库服务`
  - `检索工具底层基于 embedding 和向量索引召回相关内容`
  - `再把结果返回给模型用于生成`
- 区分三层：
  - `MCP` 是模型调用工具的方式
  - `embedding + 向量库` 是检索实现
  - `LLM` 是拿到结果后做生成

### 6.5 RAG 是怎么“生成方案”的
- 更准确地说：
  - RAG 不直接生成方案
  - 真正生成方案的是大模型
- RAG 做的是：
  - 从知识库里检索相关知识
  - 把知识作为上下文提供给模型
- 所以一句话：
  - `RAG 负责增强上下文，LLM 负责生成结果`

## 7. 今日面试高频总结口径

### 7.1 Flink
- `Flink 通过 checkpoint 对状态和 source 位点做一致性快照，失败时从 checkpoint 恢复；再结合支持幂等或两阶段提交的 sink，最终实现端到端一致性。`
- `Watermark 是事件时间进度线，作用是触发窗口计算和判断迟到数据。`
- `Barrier 对齐就是多输入流在同一个 checkpoint 边界上对齐后再做快照。`

### 7.2 Spark
- `Spark SQL 按 action 划 Job，不是按 join 或 group by 划 Job；join/group by/order by 主要影响的是 Stage。`
- `同一条 SQL 可以因为多次 action 触发多个 Job，因为 SQL 本质上是懒执行的计算计划。`
- `执行计划生成过程是：SQL 解析 -> 逻辑计划 -> 语义分析 -> 逻辑优化 -> 物理计划 -> action 触发执行。`

### 7.3 AI / RAG
- `MetaSentry AI 采用规则 + LLM，而不是纯规则，因为很多审核问题本质上是语义判断。`
- `RAG 的核心是先检索，再生成；embedding 是 RAG 检索层的重要基础，但不等于 RAG 本身。`
