# 面试问题系统复盘 - 2026-03-17

## 1. Spark SQL 运行机制与调优

### 1.1 Spark SQL 任务从提交到结束的全过程
- Spark SQL 的执行主线是：`SQL -> 逻辑计划 -> 物理计划 -> Action 触发 Job -> Job 按 Shuffle 切 Stage -> Stage 按 Partition 拆 Task -> Driver 调度 -> Executor 执行 -> 返回/落盘结果`。
- 写 SQL 或 DataFrame 转换逻辑时，Spark 不会立刻执行，而是先形成逻辑计划和物理计划。
- 真正触发执行的是 `show`、`count`、`collect`、`write.save` 这类 `action`。
- 一个 `Job` 通常对应一次被触发的完整计算。
- 一个 `Job` 会按 `shuffle` 边界拆成多个 `Stage`。
- 一个 `Stage` 会再按 `partition` 数拆成多个 `Task`。
- `Driver` 负责生成执行计划、切分 Job/Stage/Task 并调度；`Executor` 负责真正执行 Task。

### 1.2 DAG、Job、Stage、Task 的关系
- `DAG`：由 transformation 形成的依赖图。
- `Job`：一次 action 触发的一次完整执行。
- `Stage`：Job 中按 shuffle 划分出来的执行阶段。
- `Task`：Stage 在单个分区上的执行单元。
- 关系可以记成：`Driver -> Job -> Stage -> Task -> Executor`。

### 1.3 Job 如何拆成 Stage
- 由 Spark 自动决定，更准确地说由 `DAGScheduler` 根据 `shuffle dependency` 切分。
- 关键判断依据是物理计划里的 `Exchange`/shuffle 边界。
- 没有 shuffle 的连续计算通常处于同一个 Stage。
- 遇到 `group by`、`join`、`distinct`、`order by`、`repartition` 等操作时，通常会形成新的 Stage。

### 1.4 Stage 如何拆成 Task
- 核心原则：`一个 partition 通常对应一个 Task`。
- 如果是扫描阶段，partition 通常来自数据源切片，例如文件 split、Kafka partition。
- 如果是 shuffle 后阶段，partition 通常来自：
  - `spark.sql.shuffle.partitions`
  - `repartition(n)` 显式指定
  - AQE 动态调整

### 1.5 Shuffle 发生在哪
- Shuffle 不是单独某一个 Stage，而是两个 Stage 之间的分界动作。
- 上一个 Stage 负责把结果按 key 重分区并写出 shuffle 数据。
- 下一个 Stage 负责读取 shuffle 数据并继续计算。

### 1.6 什么是 Action
- Action 是真正触发执行的操作。
- 常见 action：
  - `show`
  - `count`
  - `collect`
  - `take`
  - `write.save`
- `where`、`filter`、`case when`、`group by`、`sum` 等通常只是 transformation 或执行计划的一部分，本身不一定立即触发执行。
- 要区分：
  - 聚合逻辑不等于 action
  - action 才是执行开关

### 1.7 Spark SQL 常见调优思路
- 减少输入数据量：
  - 分区裁剪
  - 谓词下推
  - 列裁剪
- 减少 shuffle：
  - broadcast join
  - 避免无意义 distinct
  - 合理设计 join 顺序
- 处理数据倾斜：
  - 热 key 打散
  - 热点与非热点拆开处理
  - AQE skew join 优化
- 合理控制并行度与分区数：
  - 分区过少会资源吃不满
  - 分区过多会产生调度开销
- 正确使用缓存与内存：
  - cache/persist 要基于复用价值
  - 避免广播过大或缓存过多导致 OOM

### 1.8 如何解决数据倾斜
- 先识别是否是真正倾斜：
  - 少数 task 极慢
  - 个别分区特别大
- 常见解决手段：
  - 小表广播，避免双边 shuffle
  - 对热点 key 做打散（salting）
  - 热点 key 和非热点 key 分开处理
  - 预聚合，减少 shuffle 量
  - 利用 AQE 自动优化 skew join
- 本质：不是让所有 task 更快，而是避免热点 key 把某个 task 压死。

### 1.9 Broadcast Join 原理
- 核心原理：`把小表复制到每个 Executor 上，让大表在本地和小表做 join，从而避免双边 shuffle`。
- 典型适合场景：大事实表 join 小维表。
- Spark SQL 中常见物理实现是 `BroadcastHashJoin`。

## 2. 数仓建模与数据治理

### 2.1 大数据建模经验
- 先做业务抽象，再做表设计：
  - 业务对象是什么
  - 事实过程是什么
  - 分析粒度是什么
  - 指标口径是什么
- 分层建模要稳定：
  - ODS 贴源
  - DWD 做统一明细口径
  - DWS 做主题汇总
  - ADS 面向具体应用
- 粒度和口径统一比字段多更重要。
- 在底层保持规范，在汇总层适当反规范化。
- 提前考虑增量、实时、回溯和模型演进。

### 2.2 星型模型和雪花模型
- 星型模型：
  - 事实表在中心
  - 周围直接挂较宽的维度表
  - 查询简单、join 链路短
- 雪花模型：
  - 维度表继续拆成更细的子维表
  - 结构更规范、冗余更少
  - 但查询更复杂
- 一句话：
  - 星型：少拆表、方便查
  - 雪花：多拆表、更规范

### 2.3 缓慢变化维 SCD
- 缓慢变化维：维度数据会变化，但变化频率低于事实数据。
- 常见类型：
  - Type 1：直接覆盖，不保留历史
  - Type 2：新增记录保留历史，常见于拉链表
  - Type 3：保留有限历史
- 实践中最常见的是：
  - 不关心历史时用 Type 1
  - 需要历史追溯时用 Type 2

### 2.4 是否有“快速变化维”
- 实务上很少正式称为“快速变化维”。
- 如果一个所谓维度变化太频繁，通常更适合建成：
  - 事实流水表
  - 快照表
  - 状态表
- 例如库存、余额、实时状态，往往已更像事实或状态，而不是典型维度。

### 2.5 数据治理最佳实践
- 先统一标准：
  - 命名规范
  - 分层规范
  - 指标口径
  - 元数据要求
- 数据质量治理要规则化 + 责任化。
- 元数据和血缘是治理底座。
- 治理应尽量前置到开发流程，而不是只靠事后补救。
- 权限治理与分级分类要同步建设。
- 治理要形成闭环：
  - 发现问题
  - 定位 owner
  - 推动修复
  - 验证结果
  - 沉淀规则

### 2.6 如何评估数据质量
- 常见维度：
  - 完整性
  - 准确性
  - 一致性
  - 唯一性
  - 时效性
- 评估方法：
  - 空值率、重复率、波动阈值校验
  - 上下游对账
  - 时效监控
  - 核心指标异常检测
- 数据质量不是抽象概念，要落成规则、监控和责任闭环。

## 3. SQL 窗口函数与展开函数

### 3.1 窗口函数是什么
- 窗口函数的作用是：`在不折叠明细行的前提下，对分组或排序窗口内的数据做统计/排序/偏移计算`。
- 与 `group by` 最大区别：
  - `group by` 会把多行聚成一行
  - 窗口函数保留每一行明细

### 3.2 排名类窗口函数
- `row_number()`：
  - 每行唯一编号
  - 不考虑并列
- `rank()`：
  - 并列同名次
  - 后续跳号
- `dense_rank()`：
  - 并列同名次
  - 后续不跳号

### 3.3 lag 和 lead
- `lag(col, 1)`：
  - 取当前行前一行的值
- `lead(col, 1)`：
  - 取当前行后一行的值
- 常用于：
  - 环比
  - 前后状态比较
  - 取上一单 / 下一单

### 3.4 explode
- 作用：把一行中的数组、集合或 map 展开成多行。
- 常见写法：
  - `explode(arr_col)`
  - `explode(split(tags, ','))`
- 核心理解：`把一行里的多个值拆成多行里的单个值`

### 3.5 posexplode
- 作用：在展开多行的同时保留元素位置索引。
- 比 `explode` 多返回一个位置列。
- 可以理解成：`posexplode = explode + pos`
- 例子：
  - `explode(split('a,b,c', ','))` 只得到 `a b c`
  - `posexplode(split('a,b,c', ','))` 会得到 `(0,a) (1,b) (2,c)`

### 3.6 `lateral view posexplode(split(tags, ',')) tmp as pos, tag` 的含义
- `split(tags, ',')`：
  - 先把字符串拆成数组
- `posexplode(...)`：
  - 再把数组展开成多行，并返回位置和值
- `lateral view`：
  - 把展开结果附着回原表这一行
- `tmp as pos, tag`：
  - 给展开后的两列命名为 `pos` 和 `tag`

## 4. RAG 与向量检索

### 4.1 RAG 原理
- `RAG = Retrieval-Augmented Generation`
- 核心流程：
  - 先检索相关资料
  - 再让大模型基于资料生成答案
- 离线阶段：
  - 收集文档
  - 切分 chunk
  - 做 embedding
  - 建向量索引
- 在线阶段：
  - 用户提问
  - 对问题做向量化
  - 检索相关文档
  - 把文档片段拼到 prompt 里
  - 让模型回答
- 价值：
  - 能接私有知识
  - 减少幻觉
  - 支持知识更新
  - 更可追溯

### 4.2 向量检索为什么能做语义搜索
- 因为 embedding 模型会把文本映射到一个语义空间中。
- 在这个空间里：
  - 语义相近的文本向量更接近
  - 语义不相关的文本向量更远
- 检索时不是做字面匹配，而是做向量相似度比较。

### 4.3 为什么语义相似的向量会靠近
- 不是天然如此，而是模型训练目标刻意学出来的。
- 模型在训练时会不断学习：
  - 哪些文本对是相关的
  - 哪些文本对是不相关的
- 训练目标推动相关文本向量更近，不相关文本更远。

### 4.4 中文和英文的语义空间是否一样
- 不一定，要看 embedding 模型是否做了跨语言对齐。
- 单语模型：
  - 中文内部成空间
  - 英文内部成空间
  - 中英文不一定能直接对齐
- 多语模型：
  - 训练时会尽量把不同语言中语义相同的内容映射到更接近的区域

## 5. MetaSentry AI 项目复盘

### 5.1 项目定位
- MetaSentry AI 是一个“指标资产智能审核系统”。
- 要解决的问题：
  - 命名不统一
  - 定义不清
  - 指标口径重复
  - 依赖关系不合理
  - 资产重复建设

### 5.2 项目背景
- 团队持续新建指标资产。
- 原来主要靠人工审核，效率低、标准不稳定。
- 目标是把审核流程自动化，并前置到资产创建阶段。

### 5.3 为什么用 LLM
- 一部分问题适合规则：
  - 必填
  - 格式
  - 枚举
  - 命名结构
- 一部分问题需要语义判断：
  - 定义是否完整
  - 名称是否规范
  - 名称和定义是否一致
  - 是否存在语义冲突
- 因此采用：
  - `规则 + LLM`
  - 而不是纯规则或纯大模型

### 5.4 系统架构
- 交互层：
  - 前端表单
  - 字段级实时校验
  - 完整资产审核
- 接口层：
  - Spring Boot 提供审核接口
- 审核编排层：
  - 拆成不同审核任务
  - 例如命名、定义、一致性、依赖、冲突
- 模型与规则层：
  - 确定性问题走规则
  - 语义问题交给 LLM
  - 输出结构化结果

### 5.5 工作流设计
- 字段级实时校验：
  - 用户填写字段
  - 前端调用单字段接口
  - 后端先做规则校验
  - 必要时调 LLM
  - 返回结构化反馈
- 完整资产审核：
  - 用户提交完整指标表单
  - 后端拆多个审核任务
  - 聚合成完整审核报告

### 5.6 规则和规范
- 结构化规则：
  - 必填校验
  - 命名结构
  - 指标类型约束
  - 依赖类型限制
- 语义规则：
  - 定义完整性
  - 名称与定义一致性
  - 业务过程和量化对象匹配
  - 存量指标语义冲突

### 5.7 LLM 设计难点
- 规则和语义问题混合：
  - 解决方法：规则优先，LLM 补语义
- Prompt 太泛容易漂：
  - 解决方法：加入明确规范、上下文和输出约束
- 输出不稳定：
  - 解决方法：强约束结构化输出
- 实时与完整审核要求不同：
  - 解决方法：拆成轻量和重量两条链路
- 跨字段依赖：
  - 解决方法：按任务裁剪上下文

### 5.8 项目如何在面试里表达
- 背景：
  - 指标资产审核过于依赖人工
- 目标：
  - 在创建阶段做自动化审核
- 方法：
  - 字段级实时校验 + 完整资产审核
  - 规则 + LLM
- 难点：
  - 规范沉淀、语义判断、结构化输出、流程前置

## 7. “小数点”智能答疑体系复盘

### 7.1 项目背景
- 数据团队日常会收到大量咨询：
  - 指标口径怎么理解
  - 某张表怎么用
  - SQL 怎么写
  - 某类问题该找谁
- 如果完全靠人工答疑：
  - 成本高
  - 响应慢
  - 同类问题重复出现
  - 知识难沉淀
- 这个项目的目标不是做一个“万能聊天机器人”，而是让高频数据咨询先被系统承接和匹配。

### 7.2 项目输入与知识沉淀
- 我做了三类基础建设：
  - 清洗分析约 `6000` 条历史问题
  - 做 `20+` 次业务访谈，理解真实提问习惯和场景
  - 整理 `15+` 份高频 QA / Wiki 资料
- 这一步的价值是：
  - 先把“问题类型”摸清楚
  - 再决定适合规则、检索还是大模型
- 面试里可以强调：
  - `先做知识整理和问题归类，再做智能化，不是一上来直接接 LLM`

### 7.3 系统思路怎么讲
- 一个稳妥的表达方式是：
  - 先做问题归类
  - 再做知识匹配
  - 最后决定返回标准答案、候选资料，还是进入更复杂的生成链路
- 这样设计的原因：
  - 高频标准问题不需要每次都让大模型自由生成
  - 先匹配知识可以降低幻觉
  - 也更容易做效果评估和持续迭代

### 7.4 为什么不能只靠关键词搜索
- 因为真实用户提问不标准：
  - 同一个问题有很多表达方式
  - 提问里常带大量上下文噪音
  - 有时问的是表面现象，不是根问题
- 所以系统要解决的不只是“搜到文档”，而是：
  - 识别问题意图
  - 对齐相似问法
  - 把问题映射到可复用知识

### 7.5 这个项目的难点
- 历史问题质量不齐：
  - 有些问题表述很短
  - 有些问题缺少上下文
  - 有些问题本质上是重复问题
- 知识来源分散：
  - Wiki、IM、人工经验、口头规则都可能是知识源
- 效果评估不简单：
  - 不是只看“答没答出来”
  - 还要看是否真的减少人工介入

### 7.6 你在里面的核心价值怎么讲
- 我的核心工作不是单纯“调模型”，而是：
  - 做历史问题清洗与模式归纳
  - 沉淀高频知识库
  - 设计问题分类和匹配思路
  - 推动答疑从人工应答走向可复用、可运营的体系
- 结果可以直接讲：
  - `问题分类人力由 1 PD 降到 0.1 PD`

### 7.7 面试里的项目表达模板
- 背景：
  - 数据咨询问题很多，人工答疑重复且低效
- 目标：
  - 把高频咨询先标准化、知识化，再用智能匹配提升响应效率
- 方法：
  - 清洗历史问题
  - 访谈业务团队
  - 整理 QA / Wiki
  - 建立问题分类与知识匹配机制
- 结果：
  - 显著减少人工分类成本，推动咨询流程标准化

### 7.8 高频追问
- 为什么不直接做纯 RAG？
  - 因为不是所有问题都适合自由问答，很多高频问题更适合先分类和标准匹配，稳定性更高。
- 为什么不直接纯规则？
  - 因为用户提问表达差异很大，纯规则覆盖不了语义相近但字面不同的问题。
- 你怎么衡量效果？
  - 可以从命中率、人工接管率、问题分类成本、用户反馈等维度看，核心是是否真的减少重复人工支持。

## 8. 订单域标准化建设复盘

### 8.1 项目背景
- 订单域通常是数据使用最频繁、口径分歧也最容易出现的区域。
- 随着业务发展，常见问题会越来越明显：
  - 同名不同义
  - 同义不同名
  - 维度定义不统一
  - 同一指标在不同模型里重复建设
- 这类问题如果不治理，后面会带来：
  - 开发重复
  - 指标口径争议
  - 跨团队协作成本高

### 8.2 你做了什么
- 盘点订单域资产：
  - `83` 个指标收敛为 `47` 个高频指标
  - `43` 个维度收敛为 `27` 个高频维度
- 从 `14` 个业务模型中抽象出 `6` 个通用基建模型。
- 同时配套建设：
  - 词根 / 维度校验机制
  - SQL 映射工具
- 最终效果：
  - `60` 个指标维度录入耗时由 `2-3 PD` 降到 `0.5 PD`
  - 高频场景标准化覆盖约 `80%`

### 8.3 这个项目的本质
- 这个项目本质上不是“整理文档”，而是：
  - 统一业务语言
  - 统一指标口径
  - 统一模型抽象
  - 把标准嵌到开发流程里
- 面试里可以强调：
  - `标准化最难的不是写规范，而是让规范进入真实生产流程`

### 8.4 难点怎么讲
- 难点一：历史资产很多，且命名和口径不统一
  - 需要先盘点，再归并，再抽象
- 难点二：业务模型和通用模型之间存在张力
  - 过于通用会失去可用性
  - 过于业务化又难复用
- 难点三：如果只有人工治理，成本太高
  - 所以要把规则工具化、流程化

### 8.5 词根 / 维度校验和 SQL 映射工具怎么答
- 一个稳妥说法是：
  - 用词根约束指标命名核心语义
  - 用维度规则约束维度使用范围和表达方式
  - 通过 SQL 映射辅助识别已有实现与标准定义的对应关系
- 这套机制的价值：
  - 降低新建资产时的随意性
  - 提高复用率
  - 把标准化从“靠人记”变成“靠系统校验”

### 8.6 你在项目里的角色怎么讲
- 你可以突出三件事：
  - 做资产盘点与问题归类
  - 推动指标/维度/模型收敛
  - 把规范沉淀成工具和校验机制
- 这会比只说“我做了治理”更有说服力。

### 8.7 高频追问
- 为什么最后是 `47` 个指标、`27` 个维度？
  - 因为治理目标不是把所有东西删到最少，而是保留高频共性口径，让大部分场景优先复用。
- 怎么判断一个指标该保留还是收敛？
  - 看业务通用性、使用频次、口径稳定性和替代关系。
- 业务方不接受统一口径怎么办？
  - 先区分“真实业务差异”还是“历史命名差异”，前者保留差异，后者推动收敛。

## 9. 国补数据链路与治理复盘

### 9.1 项目背景
- 国补相关场景通常有几个明显特点：
  - 时效要求高
  - 审计要求严
  - 口径必须稳定
  - 需要同时服务经营分析和外部报送
- 这种项目不能只追求“能出数”，更关键的是：
  - 稳定
  - 可解释
  - 可追溯

### 9.2 你做了什么
- 建设核心数据链路和数据产品体系：
  - 改造融合 `12` 张 Fact / Aggr 基建表
  - 建立 `11` 个 DQC 监控项
  - 保障政府审计数据每日 `03:00`、经营数据每日 `07:00` 稳定交付
  - 开发 `9` 个可视化组件并上线 `33` 个看板
- 推动审计自动化与治理闭环：
  - 覆盖 `19` 省 / 直辖市、`74` 地市
  - 融合 `2` 个通用报账模板与 `74` 条明细数据
  - 报送打回率下降约 `30%`
  - 业务侧口径反馈率由 `20%` 降到 `8%`

### 9.3 这个项目的亮点
- 亮点不是单点开发，而是打通了完整链路：
  - 底层事实与汇总建模
  - 数据质量监控
  - 报送自动化
  - 看板产品化
  - 口径治理闭环
- 这说明你做的不只是 ETL，而是：
  - `数据链路建设 + 稳定性交付 + 业务治理`

### 9.4 DQC 价值怎么讲
- DQC 不是为了“好看”，而是为了把问题前置发现。
- 在这种强时效场景下，DQC 解决的是：
  - 当天能不能按时交付
  - 口径漂没漂
  - 上游异常有没有及时暴露
- 面试时一句话即可：
  - `DQC 的目标不是补救，而是尽量在报送和看板使用前拦截异常`

### 9.5 难点怎么讲
- 多地区口径和报送要求复杂
- 上下游链路长，任何一段异常都可能影响最终交付
- 审计和经营两类场景对数据使用方式不同，但底层口径又必须一致
- 这类项目最大的难点通常不是写 SQL，而是稳定性和治理闭环

### 9.6 面试里的项目表达模板
- 背景：
  - 国补场景数据时效和审计要求高，原有链路分散，口径反馈较多
- 目标：
  - 建立稳定、可追溯、可治理的数据链路和报送体系
- 方法：
  - 重构 Fact / Aggr 基建表
  - 建 DQC
  - 做报送自动化
  - 建可视化产品
- 结果：
  - 稳定保障 SLA
  - 降低打回率
  - 降低业务口径反馈

### 9.7 高频追问
- 为什么要做 Fact / Aggr 分层？
  - 因为底层明细口径和上层报送 / 分析口径关注点不同，分层后更利于复用和治理。
- 你怎么保证 03:00 / 07:00 SLA？
  - 关键是链路拆解、依赖梳理、前置监控和异常快速定位，而不是只盯最终结果。
- 看板价值怎么体现？
  - 不是“做了几个图”，而是把分散数据变成业务可以稳定使用的产品。
