## 1. Spark 运行机制

### 1.1 Spark SQL 任务从提交到结束
- 主线可以概括为：
  `SQL -> 逻辑计划 -> 物理计划 -> Action -> Job -> Stage -> Task -> 结果输出`
- SQL / DataFrame transformation 本身通常不会立即执行。
- 真正触发执行的是 `show`、`count`、`collect`、`write` 等 `action`。
- 一个 `action` 通常对应一个 `Job`。
- `Job` 会按 `shuffle` 边界切成多个 `Stage`。
- `Stage` 再按 `partition` 拆成多个 `Task`。
- `Driver` 负责规划与调度，`Executor` 负责真正执行。

### 1.2 DAG、Job、Stage、Task 的关系
- `DAG`：transformation 形成的依赖图。
- `Job`：一次真正提交执行的完整计算任务。
- `Stage`：Job 内按 shuffle dependency 切出的阶段。
- `Task`：Stage 在单个 partition 上的执行单元。
- 记忆方式：
  `Action -> Job -> Stage -> Task`

### 1.3 Job 如何切成 Stage
- Stage 的切分依据是 `shuffle dependency`。
- 没有 shuffle 的连续算子通常放在同一个 Stage。
- 典型会形成 shuffle 边界的操作：
  - `group by`
  - `join`
  - `distinct`
  - `order by`
  - `repartition`
- 更底层一点，是 `DAGScheduler` 在根据宽依赖切 Stage。

### 1.4 Stage 如何拆成 Task
- 一个 `partition` 通常对应一个 `Task`。
- 输入阶段的 partition 常来自：
  - 文件 split
  - Kafka partition
  - 数据源切片
- shuffle 后阶段的 partition 常来自：
  - `spark.sql.shuffle.partitions`
  - `repartition(n)`
  - AQE 动态调整

### 1.5 什么是 Partition
- Partition 是 Spark 对数据做的逻辑分片。
- Task 负责处理其中一份分片。
- 简单记：
  - `Partition` 是数据切片
  - `Task` 是执行单元

### 1.6 什么是 Action
- Action 是真正触发 Spark 执行的结果型操作。
- 常见 action：
  - `df.show()`
  - `df.count()`
  - `df.collect()`
  - `df.write.save(...)`
- `where`、`case when`、`join`、`group by`、`sum` 等通常只是执行计划的一部分，不一定单独触发 action。

### 1.7 一个 Job 会划分成多少个 Stage
- 核心看该 Job 有多少个 `shuffle` 边界。
- 简化理解：
  - 0 次 shuffle -> 通常 1 个 Stage
  - 1 次 shuffle -> 通常至少 2 个 Stage
  - 多次 shuffle -> 通常更多 Stage
- 不是写死的，而是由物理执行计划和调度器决定的。

## 2. Shuffle 机制

### 2.1 为什么需要 Shuffle
- Executor 天然只拿到局部数据。
- 但很多操作要求把相关数据聚到一起，例如：
  - `group by`
  - `join`
  - `distinct`
  - `order by`
- 所以需要按新的 key 重新组织数据。

### 2.2 Shuffle 的本质
- `shuffle` 的本质是：
  `按照新的 key 重新分区和重分布数据`
- 更严谨的说法：
  不是简单搬到同一节点，而是让相关数据进入同一个 `partition`。

### 2.3 Shuffle 的执行过程
- 上游 Stage：
  - 根据目标 key 计算每条记录属于哪个 partition
  - 按 bucket 切分并写出 shuffle 文件
- 下游 Stage：
  - 从所有上游 Task 的输出中拉取属于自己 partition 的那部分数据
  - 在本地完成聚合、join、排序等
- 代价主要来自：
  - 网络传输
  - 磁盘 IO
  - 序列化 / 反序列化
  - task 等待

### 2.4 Shuffle 发生在什么阶段
- 更准确说，shuffle 发生在两个 Stage 之间。
- 上游负责写 shuffle 输出，下游负责读 shuffle 输入。

### 2.5 为什么会多次 Shuffle
- 因为复杂 SQL 里可能有多次“全局重分布需求”。
- 例如：
  - join 按 `product_id`
  - group by 按 `(shop_id, category_id)`
  - order by 按 `total_amount`
- 每个阶段依赖的 key 不同，一次 shuffle 解决不了全部问题。

## 3. Spark SQL 示例：Action、Job、Shuffle、Stage

### 示例 SQL
```sql
select
    a.shop_id,
    b.category_id,
    sum(a.amount) as total_amount
from order_detail a
join product_dim b
    on a.product_id = b.product_id
where a.dt = '2025-08-01'
group by a.shop_id, b.category_id
order by total_amount desc
```

### 3.1 Action
- 如果后面调用：
  - `df.show()`
  - `df.count()`
  - `df.write.save(...)`
- 这些才是真正的 `action`。

### 3.2 Job
- 一个 `action` 通常触发一个 `Job`。
- 上面的 SQL 如果最后只有一个 `df.show()`，通常按面试口径就是 1 个 Job。

### 3.3 Shuffle
- 可能的 shuffle 点：
  - join（如果不能 broadcast）
  - group by
  - order by
- 如果小表被 broadcast，join 那一步可能不需要 shuffle。

### 3.4 Stage
- Stage 数量由 shuffle 边界决定。
- 在上面这个例子里：
  - 如果 join 不能 broadcast，可能有 3 次 shuffle，切成更多 Stage
  - 如果 join 被 broadcast，则通常会少一个 shuffle，Stage 也更少

## 4. Spark 与 MapReduce 的关系

### 4.1 两者关系
- `MapReduce` 是经典的分布式计算模型。
- `Spark` 继承了 Map / Shuffle / Reduce 的核心思想，但扩展成了 DAG 多阶段执行。

### 4.2 Spark 与 MapReduce 的区别
- Hadoop MapReduce：
  - 更接近固定的 `Map -> Shuffle -> Reduce`
- Spark：
  - 是 DAG
  - 一个 Job 里可以有多个 map-like / reduce-like 阶段
  - 执行更灵活，通常更高效

### 4.3 Map、Shuffle、Reduce 是不是固定写死
- 经典 Hadoop MapReduce 框架的范式基本固定。
- 但具体任务中可以弱化或跳过 Reduce，例如 reduce 数设为 0。
- Spark 则不是固定两段式。

### 4.4 Shuffle 在 Map 中还是 Reduce 中
- 更准确地说：
  `Shuffle 发生在 Map 输出和 Reduce 输入之间`
- Map 侧负责：
  - 分区
  - 排序
  - 写中间文件
- Reduce 侧负责：
  - 拉取
  - 归并
  - 分组

## 5. Broadcast Join、AQE 与 Skew Join

### 5.1 Broadcast Join 原理
- 核心原理：
  `把小表广播到每个 Executor，在本地和大表分区做 join，避免双边 shuffle`
- 适合：
  - 大表 join 小表
  - 小表能安全放进 Executor 内存
- 对数据倾斜的价值：
  - 在大表 join 小表场景下，常常是解决 join 倾斜的首选方案

### 5.2 大表 join 大表怎么处理倾斜
- Broadcast join 通常不适用。
- 常见手段：
  - 热点 key salting 打散
  - 热点与非热点分开处理
  - AQE + skew join
  - 预聚合、先过滤、先压缩数据量

### 5.3 AQE 是什么
- `AQE = Adaptive Query Execution`
- 原理：
  `先按静态计划运行，跑到 shuffle 后拿到真实统计信息，再动态改后续计划`
- 常做的事：
  - 合并过小分区
  - 识别倾斜
  - 某些场景下调整 join 策略

### 5.4 Skew Join 是什么
- 原理：
  `发现某些 join partition 特别大后，把这些热点 partition 拆成多个小任务来跑`
- 它的目标不是改 join 结果，而是防止热点 key 把单个 task 压爆。

### 5.5 AQE 和 Skew Join 的关系
- `AQE` 是运行时动态优化框架。
- `skew join` 是 AQE 里的一个专项优化能力。
- 通常需要：
  - `spark.sql.adaptive.enabled=true`
  - 再配合 `spark.sql.adaptive.skewJoin.enabled=true`

## 6. 与 Shuffle 失败相关的参数优化理解

### 6.1 原来为什么跑不动
- 典型现象：
  - 某个 Stage 的 shuffle read / fetch 失败
- 常见根因：
  - 数据倾斜
  - 单个 partition 太大
  - shuffle 分区不合理
  - 网络拉取超时
  - 小文件 / 小分区过多

### 6.2 优化后为什么能跑了
- 核心是几类措施一起起作用：
  - AQE 动态调整分区
  - skew join 自动拆分热点分区
  - 提高 timeout，避免大 partition 还没拉完就被判失败
  - 压缩 shuffle，降低 IO 和网络开销
  - 合并小文件，降低碎 task 和碎 block 问题

### 6.3 参数中的重点理解
- `spark.sql.shuffle.partitions`
  - 控制 shuffle 后默认切多少个 partition
- `spark.sql.adaptive.enabled`
  - 开启 AQE
- `spark.sql.adaptive.skewJoin.enabled`
  - 开启 skew join 倾斜优化
- `spark.network.timeout` / `spark.sql.broadcastTimeout`
  - 放宽超时
- 压缩相关参数：
  - 降低 shuffle 网络与磁盘开销

## 7. 谓词下推

### 7.1 什么是谓词下推
- 谓词下推就是：
  `把 where 条件尽可能往数据源方向推，让数据越早被过滤掉越好`

### 7.2 价值
- 少读数据
- 少传数据
- 少做后续计算

### 7.3 常见场景
- 分区裁剪
- Parquet / ORC 读取裁剪
- JDBC 下推到数据库执行

## 8. 数据开发与数仓基础问题

### 8.1 一二三范式
- `1NF`：字段原子化
- `2NF`：非主键字段必须完全依赖主键，消除部分依赖
- `3NF`：非主键字段不能依赖其他非主键字段，消除传递依赖

### 8.2 数据治理最佳实践
- 统一标准：
  - 命名、分层、指标口径、元数据
- 做质量治理：
  - 完整性、准确性、一致性、唯一性、时效性
- 元数据和血缘是治理底座
- 治理前置到开发流程中
- 权限和分级分类同步建设

### 8.3 如何评估数据质量
- 重点看：
  - 完整性
  - 准确性
  - 一致性
  - 唯一性
  - 时效性

## 9. SQL 函数和窗口函数

### 9.1 窗口函数
- 保留明细行的同时，做分组内统计、排序或偏移分析。

### 9.2 排名类函数
- `row_number()`：不考虑并列
- `rank()`：并列同名次，后面跳号
- `dense_rank()`：并列同名次，后面不跳号

### 9.3 lag / lead
- `lag`：取前一行
- `lead`：取后一行
- 常用于环比、前后状态对比

### 9.4 explode / posexplode
- `explode`：
  - 把数组或多值字段展开成多行
- `posexplode`：
  - 展开成多行时，同时保留位置索引
- 典型示例：
  - `explode(split(tags, ','))`
  - `posexplode(split(tags, ','))`

### 9.5 `lateral view posexplode(...)`
- 含义：
  - 先把字段切成数组
  - 再展开为多行
  - 并把位置和值命名成新列
